# TaskOS to Supabase Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Circle's mock project/issue persistence with two isolated Supabase workspaces and import TaskOS data from Neon into the work workspace.

**Architecture:** Supabase Auth establishes cookie-backed SSR sessions; every domain row carries `workspace_id` and is protected by membership-based RLS. A server-only, idempotent migration script reads Neon, provisions the work workspace, maps TaskOS projects/tasks/time entries to Circle entities, and verifies exact source/target counts.

**Tech Stack:** Next.js 15 App Router, React 19, TypeScript, `@supabase/ssr`, `@supabase/supabase-js`, Zod, Zustand, Vitest, Neon serverless driver, pnpm.

**Spec:** `docs/superpowers/specs/2026-08-25-taskos-supabase-migration-design.md`

## Global Constraints

- Supabase project is `abazmhlhnccdfjwmojvs`.
- Google and Microsoft/Azure are the only sign-in providers; Microsoft personal accounts use the `consumers` tenant.
- Exactly two allowlisted accounts receive workspaces: one `work`, one `freelance`.
- Every exposed table has RLS and every mutation enforces workspace membership.
- Never expose a Supabase secret/service-role key to client code.
- Preserve all TaskOS UUIDs, 18 projects, 371 tasks, 374 time entries, 14 requesters, and 7 parent links.
- Neon remains unchanged and acts as rollback source.
- Work and freelance data must be mutually inaccessible for SELECT, INSERT, UPDATE, and DELETE.
